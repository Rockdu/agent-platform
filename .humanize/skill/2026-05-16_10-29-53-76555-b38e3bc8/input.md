# Required Output

Sections (exact `##` headings):

## Overview
- Why confirm-on-write exists: claude can call any plugin tool including writes; user MUST sign off each write.
- Scope: plugin-mediated MCP write tools (gmail.send, gmail.label, papers.add, terminal_mesh.write_stdin via orchestrator, etc.).
- Out-of-scope (the honesty boundary): raw filesystem writes by claude inside its workspace dir using its own Edit/Write tools.

## Request Protocol
- Sidecar sends `RequestApproval { operation_id: Uuid, plugin_id, action: String, payload: Value, severity: ConfirmSeverity }` to the host arbiter via MCP tool invocation or dedicated Tauri command.
- Arbiter enqueues if another modal is open; opens immediately if free.
- Host returns: `Approved { operation_id }` OR `Rejected { reason: String }` via `oneshot` channel.
- Sidecar HOLDS the request until reply; does NOT proceed with the external write before reply.

## Operation ID Idempotency
- `operation_id` is a UUIDv4 generated by the sidecar BEFORE the first approval request.
- Sidecar MUST reuse the SAME `operation_id` on retry (e.g., transient network error during the external API call).
- Arbiter maintains a `OperationIdCache: LruCache<Uuid, ApprovalResult>` keyed by `operation_id` with TTL ~5 minutes.
- Behavior:
  - First request with new `operation_id` → open modal, await user.
  - Retry request with same `operation_id` against a cached `Approved` → arbiter returns the cached approval immediately (no second modal); sidecar proceeds with retry against external API.
  - Retry against cached `Rejected` → arbiter returns the cached rejection.
  - Different `operation_id` → treated as new request (fresh modal).
- Why TTL ~5 min: long enough for typical retry windows; short enough that stale cached approvals don't unexpectedly authorize future operations.

## Modal UI Contract
- Single-modal-at-a-time: a `ModalCoordinator` in the host ensures NO other modal (workspace switcher, confirm-on-write, bootstrap error card) opens on top of an active confirm modal.
- Modal contents:
  - Title: action description in Chinese (e.g., "claude 想发送邮件给 alice@example.com").
  - Subtitle: target plugin name.
  - Payload preview area (scrollable): recipient/subject/body for Gmail; tag/label name + target message for label ops; etc. Plugin-specific renderer chosen by `plugin_id`.
  - "确认" + "取消" buttons.
  - Operation ID (small text at bottom for debug; not prominent).
- Per-tab pending indicator: tabs whose claude has a queued request show a "等待批准" badge.

## Queue Behavior
- FIFO; arbiter pops next request when current modal resolves.
- Cancel propagates back as `Rejected { reason: "user_cancelled" }`.
- Timeout: requests older than 5 minutes still queued get auto-`Rejected { reason: "approval_timeout" }`; modal does NOT auto-open for them.
- Bulk queue indicator: small toast or tab badge "N pending approvals" when queue depth > 1.

## Terminal Stdin Special Case (AC-7.4)
- When orchestrator's claude wants to write stdin into another tab's PTY: it calls `terminal_mesh.write_stdin(tab_id, bytes)`.
- That call is a plugin-mediated write → confirm-on-write modal opens.
- During the modal:
  - The destination PTY's OUTPUT stream continues rendering (Tokio actor's output broadcast does not pause).
  - Resize events (SIGWINCH) propagate normally.
  - Exit observation works normally (child exit → Exit event → notification).
  - ONLY the stdin write itself is paused (held in the sidecar's oneshot wait).
- If user cancels: `Rejected { reason: "user_cancelled" }`; no bytes injected; PTY state unchanged.
- If user approves: bytes written atomically; idempotent on retry (same operation_id).

## Error Cases
- Arbiter unreachable (host process not responsive) → sidecar `RequestApproval` times out after 60 seconds; sidecar returns `OperationFailed { reason: "host_unreachable" }` to claude.
- Sidecar disconnects before reply → modal auto-closes; pending approval is dropped; reconnect triggers fresh request from sidecar's retry logic (new operation_id OR same — depends on sidecar choice).
- Multiple sidecars (different `client_id`s, same plugin) requesting writes concurrently → each carries its own operation_id; arbiter handles them as independent queue entries.

## Approval Audit Trail

- Logs feed into structured JSON log stream (AC-9.5).
- Useful for post-hoc "what did claude do today" review.
